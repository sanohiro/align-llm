# C4-REPAIR-MEASURED checked-in gate evidence

`docs/specs/c4-repair-measured.md` is the authoritative plan; section 5.2 names the qualification
that produced everything here, and section 10 records the measured result. This directory is
separate from `eval/prompt/gate/`, which stays C6's and is not touched by this capability.

| File | Record | Producer |
| --- | --- | --- |

| `c4-repair-evaluation-evidence.json` | `PromptEvaluationEvidence`, `schema_version: 2` | the same run's independent sidecar |

## What the verdict is, and what it is not

The gate is `MET` when `corpus_aggregate.repair_recovery_paired_count >= 1` — at least one
(task, variant) pair recorded attempt 1 `FAIL` and attempt 2 `PASS` in **both** of its paired
samples. It consumes nothing else. The evaluation's own `status` and `gate_eligible` are the C6
acceptance verdict and are recorded alongside as secondary evidence; a candidate that repairs its
way to a pass legitimately looks *slower* and may look *worse* under the C6 acceptance policy, and
that policy is reused byte-identical and is not relaxed to make this measurement look better.

**A `NOT_MET` result is a delivered result.** The mechanism is proved by the run whether or not the
model recovers: a run in which every repair attempt is made, is measured, is bounded, is contained,
and fails proves the loop and refutes the model on these three tasks. The reporting for both
outcomes was fixed in the plan before the run, so the result cannot be re-framed after seeing it.

## What is measured and what is not claimed

`generation_to_passing_patch_ns` is evaluator-observed at version 2 and includes the repair
attempt, per spec section 3.6. It is **not comparable** to the version-1 numbers in
`eval/prompt/gate/`: it is a superset that includes per-attempt adapter overhead and repair-prompt
assembly. `adapter_overhead_ns` publishes the size of that difference on every passing attempt.

**No speed claim of any kind is made.** The two version-1 timings for one identical prompt at
temperature 0 differ by 3.5x (81.12 s and 23.40 s), so `n=2` supports no baseline, no spread, and
no floor to clear. No prompt-quality claim, no provider-quality claim, and no generality claim is
made either: one model, one build, one host, one seed, three tasks, one repository family.

## The disclosed residue

`measurement.diagnostic_stderr` in these rows contains a run-specific sandbox temp path of the form
`/tmp/align-llm-coding-task-<mkdtemp>`, generated by the frozen `eval/runners/run-coding-task.py`
and inherited verbatim into the repair prompt. It is carried deliberately: scrubbing it here would
break the section 4.4 re-derivation and put a second, divergent copy of the diagnostics in the
evidence. The correct fix is upstream in the runner or the adapter, both frozen corpus members; it
is a named deferral in spec section 5.4. It is a temp directory name, not a secret — no user path,
no home directory, no credential, no host identity.

## Reproducing

```text
python3 scripts/probe-provider-service \
  --server-path /opt/homebrew/bin/llama-server \
  --model-path ~/models/qwen2.5-coder-7b-instruct-q4_k_m.gguf \
  --generation-policy eval/prompt/canonical-v1r/generation-policy.json \
  --out <probe.json>

make c4-repair-gate \
  C4_REPAIR_SCOPE=eval/prompt/canonical-v1r/scope.json \
  C4_REPAIR_PROVIDER_PROBE=<probe.json> \
  C4_REPAIR_OUT=eval/prompt/c4-repair-gate/
```

The probe fails closed unless the host's llama.cpp build, server binary digest, and model digest all
equal `canonical-v1r/generation-policy.json`'s `provider_service_revision`; the answering server's
advertised model id is checked in band as the second half of the pair. Neither check observes that
the process answering the endpoint is the process whose binary was hashed — spec section 3.5 states
that residual risk rather than resolving it.
